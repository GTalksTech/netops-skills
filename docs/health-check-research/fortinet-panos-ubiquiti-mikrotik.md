# Read-only health check research: FortiGate / FortiSwitch / PAN-OS / Ubiquiti / MikroTik / vendor-neutral

Researched 2026-11-07. Session had limited fetch budget (4 search results + 1 page fetch + 3 searches), so evidence is graded:

- **[V]** = URL surfaced in a search this session and its claim was read in the snippet or fetched page.
- **[K]** = engineer knowledge of the command/behaviour; a doc URL is given as a landing point but was NOT fetched. Treat as "verify on a lab device before shipping into the skill".
- **[OP]** = stated operational reason only (no vendor doc cited).

Tier: 1 = vendor doc/KB, 2 = practitioner, 3 = forum.

Severity key: CRIT (act now), WARN (act this week), INFO (record only).

## 0. Cross-cutting findings that change skill design

1. **FortiOS read-only admin cannot run `diagnose` by default.** Before 6.4.0 read-only admins had no diagnose rights. From 6.4.0 the accprofile option `system-diagnostics` enables it for read-only profiles; newer releases use `cli-diagnose` (7.4.2+ per community post), and 7.4.4 added more granularity. `cli-exec` governs `execute`. Some diagnose commands still fail under read-only. [V] Tier 1: https://kb.fortinet.com/t5/FortiGate/Technical-Tip-Granting-read-only-admins-with-diagnose-commands/ta-p/223742 ; https://community.fortinet.com/t5/FortiGate/Technical-Tip-How-to-enable-debugging-for-administrators-who-are/ta-p/271415 ; Ansible accprofile schema (cli_diagnose, cli_exec): https://ansible-galaxy-fortios-docs.readthedocs.io/en/2.2.3/gen/fortios_system_accprofile.html (Tier 2). **Skill implication:** the health check should provision a dedicated audit accprofile (read on all groups, `cli-diagnose enable`, `cli-get`/`cli-show` enabled, no `cli-config`) and record "permission denied" as UNKNOWN, not as healthy.
2. **FortiOS: `execute` is not read-only in general** (`execute reboot`, `execute factoryreset` live in the same tree). Whitelist only: `execute log display`, `execute log filter ...` (session-local filter setting), `execute date`, `execute time`, `execute ping`, `execute traceroute`, `execute tac report` (heavy; generates large output). [K]/[OP]
3. **PAN-OS `request ...` and `debug ...` are not read-only-safe.** `request license info` and `request system software info` only read, but the `request` tree also contains installs/restarts. Whitelist exact strings. The `superreader`/"Device Admin (read-only)" CLI role runs `show`; `debug` generally needs superuser. [K] https://docs.paloaltonetworks.com/pan-os/11-1/pan-os-admin/firewall-administration/manage-firewall-administrators/administrative-role-types
4. **Ubiquiti UniFi switches have no vendor CLI documentation for health.** Real health data is in the UniFi Network controller API / `mca-dump` on the device, not a Cisco-like `show`. EdgeSwitch and EdgeRouter do have a CLI. [K] (searches for EdgeOS command syntax returned nothing authoritative; see section 4).
5. **MikroTik `/system package update check-for-updates` contacts the internet** and is not purely local-read; list as optional. `/system health` sensors vary by board; absence is not a failure. [V] https://mikrotik-docs.pages.dev/system/health/ (Tier 3 mirror, not official).
6. Pager hazard on EdgeOS: custom pager can hang automation; set terminal length / use `--no-pager` style env. [V] https://docs.ansible.com/ansible/latest/modules/edgeos_command_module.html (Tier 2)

FortiOS notes
- Read-only audit admin: `config system accprofile` -> `set secfabgrp read`, `set ftviewgrp read`, `set authgrp read`, `set sysgrp read`, `set netgrp read`, `set loggrp read`, `set fwgrp read`, `set vpngrp read`, `set utmgrp read`, `set wifi read`, plus `set system-diagnostics enable` (6.4-7.4.1) / `cli-diagnose enable` (7.4.2+). Names changed across versions: detect by `show system accprofile` rather than assuming. [V] KB above.
- VDOMs: run `get system status` first; with multi-VDOM, per-VDOM commands need `config vdom` / `edit <name>` and the audit admin must be in the right scope; global-only checks (HA, hardware, performance) run in `config global`. [K]

## 3. Ubiquiti

### 3a. UniFi switches (UniFi OS / UniFi Network)

No public CLI command reference for health; the supported source of truth is the UniFi Network controller (API/UI): device state, uptime, `general_temperature`, `fan_level`, `sys_stats` (CPU/mem), port table with `rx_errors`, `tx_errors`, `rx_dropped`, `tx_dropped`, `stp_state`, `poe_power`, `sfp_found` + DOM (`sfp_current`, `sfp_rxpower`, `sfp_txpower`, `sfp_temperature`). [K] UniFi Help Center https://help.ui.com/hc/en-us (landing); API is undocumented/unofficial. Tier 3: community API clients, e.g. https://github.com/Art-of-WiFi/UniFi-API-client (not fetched).

On-device via SSH (BusyBox shell; credentials = site device SSH credentials):
| Area | Command | Notes |
|---|---|---|
| Summary | `info` ; `uptime` ; `cat /proc/meminfo` / `free` ; `top -bn1 \| head -15` | `info` prints model, version, uptime, status (controller adopted) |
| Ports | `swctrl port show` ; `swctrl port show counters` (rx/tx pkts, errors, drops) ; `swctrl poe show` ; `swctrl mac show` ; `swctrl vlan show id <n>` | `swctrl` is Ubiquiti's switch utility; usage varies across model families (USW Pro/Enterprise use a newer stack) |
| Full JSON | `mca-dump` | complete device JSON including port_table, temps, SFP DOM; best on-device read |
| Logs | `logread` (or `/var/log/messages`) | |
| Controller inform | `cat /var/etc/persistent/cfg/mgmt` (inform URL) -- contains secrets? contains authkey: **do not collect** | skip |

Thresholds [OP]: same generic rules (section 5). Noise: controller shows port errors that reset with provisioning; STP state `blocking` on redundant uplinks is expected. Ubiquiti SSH access is full root shell, not read-only; use sparingly and only read commands (no config edits). This is a risk: there is no read-only SSH role on UniFi devices. [K]

### 3b. EdgeSwitch (EdgeOS-S / FASTPATH-style CLI)

Exec mode `enable`, then:
- `show version`, `show sysinfo`, `show system` (uptime, CPU, mem: `show process cpu`, `show memory`)
- `show interfaces status all` ; `show interface ethernet 0/<n>` ; `show statistics interface 0/<n>` or `show interface counters` (ifInErrors, ifInDiscards, ifOutDiscards)
- `show fiber-ports optical-transceiver all` (DOM)
- `show logging` ; `show spanning-tree summary` (TCN count, root) ; `show lldp remote-device all`
- `show port-channel all`, `show poe status`? (PoE models), `show clock`, `show sntp`
Source: Ubiquiti EdgeSwitch CLI Command Reference PDF, https://dl.ui.com/guides/edgemax/EdgeSwitch/EdgeSwitch_CLI_Command_Reference_UG.pdf (URL [K], not fetched; verify). The CLI is Broadcom FASTPATH lineage, so Cisco-like semantics apply; exact keywords differ.

### 3c. EdgeRouter (EdgeOS 2.x, Vyatta-based)

- `show version` ; `show system uptime` ; `show system memory` ; `show system cpu`? (`show hardware cpu`) ; `show system storage` ; `show system processes summary`
- `show interfaces` (up/down) ; `show interfaces counters` ; error counters: `ethtool -S eth0` (via `sudo`? read-only user can run `ethtool` in the Linux shell on most builds) or `ip -s link show eth0` (RX/TX errors, dropped, overrun)
- Routing: `show ip route summary` ; `show ip ospf neighbor` ; `show ip bgp summary` ; VPN `show vpn ipsec sa` ; `show vpn ipsec-sa` (version-dependent) 
- NTP: `show ntp` ; time `date`
- Logs: `show log` (long) ; `show log tail 200` ; `show log | match -i error`
- Offload / conntrack: `show conntrack table ipv4 count` ; `sysctl net.netfilter.nf_conntrack_max` (conntrack usage > 80% of max -> WARN)
- Hardware: no PSU/fan telemetry on most models; temperature `show hardware`? rarely.
Source: EdgeOS User Guide https://dl.ui.com/guides/edgemax/EdgeOS_UG.pdf and Ubiquiti Help https://help.ui.com/hc/en-us/categories/200321064-EdgeMAX ([K], not fetched); the ER-X manual surfaced in search without command content [V]. Pager caveat [V] https://docs.ansible.com/ansible/latest/modules/edgeos_command_module.html . EdgeOS operational mode `show` commands run as `ubnt`/read-only users (level `operator` vs `admin`): configure an `operator` level user for audit; `operator` can run `show` but not `configure`. [K]

## 5. Vendor-neutral methodology

Honest status: only a few general sources were reached this session. The thresholds below are widely used practitioner/vendor convention. No single authoritative standard exists for "80% utilisation" or "CRC > 0"; treat as defaults, expose them as config, and record the source in findings.

| Check | Threshold / pattern | Reason | Source |
|---|---|---|---|
| Interface input errors (CRC, FCS, runts, giants, align) | **Any growing count between two samples** (delta > 0) is a finding; absolute non-zero with no growth is INFO. Healthy links have ~0 | CRC/FCS means frame corrupted on wire: cable, optic, duplex mismatch, EMI | Cisco Systems, "Troubleshooting Switch Port and Interface Problems" https://www.cisco.com/c/en/us/support/docs/lan-switching/ethernet/12768-123.html [K, URL not fetched]; Cisco "Troubleshoot Input Queue Drops and Output Queue Drops" https://www.cisco.com/c/en/us/support/docs/routers/10000-series-routers/6343-queue-drops.html [K] |
| Error rate vs traffic | errors / packets > 0.001% (1e-5) sustained -> WARN; > 0.1% -> CRIT | normalises against traffic volume so busy links aren't over-flagged | [OP]/Tier 2 convention (Ethernet BER target 1e-12 is far stricter; any observed errors imply a bad link) |
| Discards / drops | output drops growing -> WARN (congestion/microbursts/buffer); input discards growing -> WARN (policing, storm control, no-buffer); ratio > 0.1% of packets -> CRIT | drops mean loss visible to apps | Cisco queue-drops doc above [K] ; Juniper "Interface statistics" https://www.juniper.net/documentation/us/en/software/junos/interfaces-ethernet/topics/ref/command/show-interfaces-extensive.html [K] |
| Utilisation | 5-min average > 70% WARN planning, > 80% WARN, > 90% CRIT; compare **peak** over the last day, not instantaneous | queueing delay rises sharply above ~80%; leave headroom for failover | widely cited practitioner rule; Cisco capacity planning notes [K] ; [OP] |
| CPU | sustained (>5 min) > 80% WARN, > 90% CRIT; spikes < 1 min ignored | control-plane starvation causes protocol flaps | Cisco "Troubleshooting High CPU" https://www.cisco.com/c/en/us/support/docs/routers/12000-series-routers/15095-highcpu.html [K] |
| Memory | free < 20% WARN, < 10% CRIT; trend: monotonic decline over days = leak, not a current fault | out-of-memory -> process death/ conserve modes | Cisco memory troubleshooting docs [K] ; vendor conserve-mode docs [V] for Fortinet |
| Spanning-tree topology changes | TCN count increasing between samples, or last TC < 1 h ago -> WARN; > N/hour (N~5) -> CRIT; unexpected root bridge change -> CRIT | loops/flapping access ports flush MAC tables and cause floods | Cisco "Understanding and Configuring STP TC" https://www.cisco.com/c/en/us/support/docs/lan-switching/spanning-tree-protocol/12013-17.html [K] |
| Adjacency (OSPF/BGP/EIGRP) | state not Full/Established for an expected neighbour -> CRIT; uptime < 1 h or flap count > 1 in 24 h -> WARN; BGP prefixes received change > 20% vs baseline -> WARN | flaps = unstable link/MTU/timers | Cisco/Juniper protocol troubleshooting guides [K] |
| Log severity | RFC 5424 severities: 0 emerg, 1 alert, 2 crit -> CRIT; 3 error -> WARN (investigate if repeated); 4 warning -> INFO unless repeated/novel; 5-7 ignore. Cluster identical messages and report counts | reduces noise; most devices spam warnings | RFC 5424 https://datatracker.ietf.org/doc/html/rfc5424 (Tier 1, standard) |
| Optics / DOM | Compare Tx/Rx power, temperature, bias, voltage to **the module's own** alarm/warning thresholds (SFF-8472 / SFF-8636), which `show interfaces transceiver detail` (Cisco) prints; Rx power within ~3 dB of low warning -> WARN; beyond alarm -> CRIT. Rule of thumb: 1.5-3 dB margin | optics degrade before link-down | SFF-8472 spec https://members.snia.org/document/dl/25916 [K] ; Cisco "Transceiver Module DOM" docs [K] |
| Time | all devices sync'd to same source; offset > 1 s WARN (logs, Kerberos, certs); > 5 min CRIT (certificate / auth failures) | log correlation and cert validity | [OP] |
| Config hygiene | running = startup (where applicable); unsaved changes -> WARN; backup age > 7 d -> WARN | reboot would lose changes | Cisco `show archive config differences` conventions [K] |
| Certificates / licences | 90/30/7 day tiers: INFO / WARN / CRIT; expired CRIT | calendar-driven outages are the most preventable | [OP] |
| Redundancy state | any redundant element (PSU, fan, HA peer, ECMP path, port-channel member) in non-redundant state is WARN even if service is up | single failure away from outage | [OP] ; vendor HA docs |
| Baseline & delta | Always take two samples (e.g. 60 s apart) for counters; compare against previous snapshot; report **delta**, not lifetime totals; clear counters only with explicit approval | lifetime counters are noisy and misleading | [OP] |

Practitioner/NANOG: I did not reach and cannot cite a specific NANOG talk or Juniper checklist this session; do not attribute claims to them in the skill. Candidates to fetch next: Juniper "Day One: Junos Health Check" / "Junos Operational Mode Health Checks" on juniper.net, Cisco "Network Health Check" in Cisco Services white papers, and NANOG archive (https://archive.nanog.org) for "interface errors" talks.
